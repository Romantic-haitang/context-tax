# MCP 工具定义到底吃掉多少

## 为什么它是最大的那笔

MCP 的代价不是"调用一次工具"，是**工具定义常驻**。每台 server 向模型声明它所有
工具的名字、用途、参数 schema，这些内容在每一轮请求里都会重新发送。

一个中等复杂度的工具（10 个参数、带嵌套对象和枚举）定义通常在 120–250 tokens。
一台暴露 15 个工具的 server，就是 2,000–3,500 tokens 的常驻开销。装 8 台，
还没开始干活，8%–14% 的窗口已经没了。

## 默认估算模型

```
每台 server tokens ≈ --mcp-tools-per-server (默认 15)
                   × --mcp-tool-tokens  (默认 150)
                   = 2,250
```

这个估算**偏保守**。真实情况：

| server 类型 | 工具数 | 每工具 tokens | 单台合计 |
| --- | --- | --- | --- |
| 文件系统 / 简单 CRUD | 5–12 | 80–150 | 500–1,500 |
| GitHub / 项目管理 | 25–60 | 150–250 | 4,000–12,000 |
| 数据库（带 schema 参数） | 5–10 | 250–400 | 1,500–4,000 |
| 浏览器自动化 | 20–40 | 120–200 | 2,500–8,000 |

所以默认值对小型 server 会高估，对 GitHub / Linear 这类会严重低估。
如果用户抱怨"数字对不上"，让他用真实工具数覆盖：

```bash
python -m context_tax . --mcp-tools-per-server 38 --mcp-tool-tokens 200
```

## 怎么拿到真实数字

最准的办法是数一下 `tools/list` 的返回体积：

```bash
# 一次请求，把 tools 列表存下来再看字节数
echo '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | <your-mcp-server-command> | wc -c
```

字节数除以 4（英文 JSON 的经验值）就是 tokens 的粗略上线。
比任何估算都准，但大部分人不会去数——这正是他们要一个工具的原因。

## 怎么跟用户说

- 不要说"你的 MCP 太多了"。要说"你的 8 台 server 里有 4 台，过去两周一次都没被调用过"。
  前提是你真的知道——不知道就别编。
- 常用的降本顺序：① 删掉不用的 server ② 换成分层的 CLI / 按需启动
  ③ 用只读的最小 server 替代全家桶 ④ 把高频操作包成一个技能，绕开工具调用
- 不要建议"全都删掉"。工具定义贵，但没有工具更贵——模型会开始靠猜。
