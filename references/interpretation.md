# 判读细则

## 税负率档位

税负率 = 常驻 tokens ÷ 上下文窗口。它回答的问题只有一句：
**你每轮有多少比例的上下文，在被和你当前任务无关的东西占着。**

| 税负率 | 等级 | 该说什么 |
| --- | --- | --- |
| < 4% | 免税 | 别硬找问题。这个配置是健康的，夸一句就够 |
| 4–8% | 轻度 | 指出占比最大的那一项，问一句"这个你上周用过吗" |
| 8–15% | 中度 | 有明确的删除对象，给出 3 条以内可执行动作 |
| 15–25% | 重度 | 上下文已经被闲置配置挤掉四分之一，用户大概率已经感觉到"变笨" |
| > 25% | 危险 | 优先砍 MCP 和重复指令，其他都是次要的 |

**不要**把税负率说成"你的配置质量分"。低税率不代表好配置，只代表便宜。

## 三类开销的分界

常驻开销（每轮都付）：
- 每个技能的 `name` + `description`
- 每台 MCP server 暴露的全部工具定义
- 无条件注入的 `CLAUDE.md` / `AGENTS.md` / `copilot-instructions.md`
- `alwaysApply: true` 的规则文件

触发税（被选中时付一次）：
- `SKILL.md` 正文。再大也不进常驻，但一触发就是全额，
  而且会挤占真正相关信息的注意力预算。

条件开销（glob 命中才付）：
- 声明了 `globs` 但没有 `alwaysApply` 的 `.cursor/rules/*.mdc`

混淆这三类是这个领域最常见的错误。别犯。

## 各类问题的应对

**触发词打架**（描述词重合度 ≥ 60%）
不是省钱问题，是选错工具的问题。两个描述相近的技能会让 agent 在同一个请求上
随机挑一个，然后你会觉得它"时好时坏"。要么合并，要么加互斥边界：
"用于 X；不用于 Y"。

**描述缺失或过短**
模型全靠 description 决定要不要加载技能。描述为空 = 这个技能永远不会触发。
补上"做什么 + 什么时候用 + 不用于什么"，三句话。

**技能正文过大且没有 references/**
把判定流程留在正文，细则、长清单、示例丢进 `references/`，让模型按需读。
判断标准：正文里有没有超过 3 屏的内容只对 10% 的情况有用。

**常驻指令过长**
超过 2,000 tokens 之后，规则本身开始互相稀释——模型会挑着执行。
只留不可推导的约定（团队特有的、反直觉的、出过事故的），其余移出去。

**MCP server 过多**
见 `mcp-tokens.md`。

## 什么时候该说"没问题"

配置健康时说"没问题"。硬找三条 nit 来证明工具有用，是这类审计工具最常见的堕落方式。
